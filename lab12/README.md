## Задание 1. Три API на одном примере

Каждый скрипт читает `data/input.txt`, переводит текст в верхний регистр и пишет результат в `data/output-sync.txt` / `output-callback.txt` / `output-promise.txt`. Затем в цикле обрабатывает `input1.txt`–`input3.txt` (→ `output-<api>-1..3.txt`). Время меряется `console.time()` / `console.timeEnd()`.

Что видно в логах (`logs/task1_*.txt`):

- **sync** — строки идут строго по порядку, итоговая фраза печатается последней: код ждал каждую операцию;
- **callback** — фраза «синхронный код закончился» печатается *первой*, а файлы завершаются не по порядку (в нашем запуске 2 → 1 → 3): все три читаются одновременно;
- **promise** — то же поведение, но код читается сверху вниз (`await`), три файла запускаются через `Promise.all`.

Замер `task1-compare.js` (200 прогонов, среднее на 3 маленьких файла, `logs/task1_compare.txt`):

| Способ | мс |
|---|---|
| sync, по очереди | 1.84 |
| promise, по очереди (`await` в цикле) | 2.89 |
| callback, параллельно | 1.15 |
| promise, параллельно (`Promise.all`) | 1.18 |

**Где быстрее и почему.** Если сравнивать «операция к операции» (по очереди), sync быстрее: асинхронный вызов передаёт задачу в пул потоков libuv, а результат возвращается через очередь event loop — на крошечном файле эти накладные расходы больше, чем само чтение. Параллельный async выигрывает, потому что три файла обрабатываются одновременно.

**Почему sync опасен на сервере.** Во время `readFileSync` поток Node.js заблокирован целиком. Во второй части замера читается файл ~20 МБ, а таймер тикает раз в 1 мс: у sync за время чтения — **0 тиков**, у callback/promise — 12–13 тиков. На сервере это значит: пока один запрос читает файл синхронно, *все остальные пользователи ждут*. Поэтому sync — только для скриптов и чтения конфигурации при старте, а в обработчиках запросов — async.

## Задание 6. Обработка ошибок (`task8-errors.js`)

| Ситуация | Код |
|---|---|
| чтение несуществующего файла | `ENOENT` |
| чтение файла без прав (chmod 000) | `EACCES` (Linux/macOS), `EPERM` (Windows) |
| чтение каталога как файла | `EISDIR` |
| файл как каталог: `readdir('plain.txt')` | `ENOTDIR` |
| путь внутрь файла `plain.txt/inner.txt` | `ENOTDIR` (Linux/macOS), `ENOENT` (Windows) |
| `writeFile(..., {flag:'wx'})` для существующего файла | `EEXIST` |
| `rmdir` непустого каталога | `ENOTEMPTY` |

Особенность Windows: `chmod(0o000)` меняет только атрибут «только чтение» — прочитать файл всё равно можно. Поэтому на Windows скрипт дополнительно запрещает чтение через ACL (`icacls файл /deny пользователь:(R)`), а в блоке `finally` возвращает права и удаляет «песочницу» `data/errors-lab/`.

## Ответы на контрольные вопросы (тема 2.3)

**1.1. Что такое fs и почему он встроен в Node.js.**
`fs` (File System) — встроенный модуль для работы с файловой системой: чтение и запись файлов, создание и удаление каталогов, получение метаданных, права, ссылки, потоки, слежение за изменениями (`fs.watch`). Встроен, потому что Node.js задумывался как среда для серверов и утилит, а им без доступа к диску не обойтись: конфиги, логи, загрузка файлов, статика. В браузере такого доступа нет из соображений безопасности, а у Node.js он есть через libuv — кроссплатформенную C-библиотеку, которая выполняет операции с диском в пуле потоков. Подключается без установки: `require('fs')`, `require('fs/promises')` или `import fs from 'node:fs'`.

**1.2. Три API модуля.**

| | Синхронный `readFileSync` | Callback `readFile(path, cb)` | Promise `fs/promises` |
|---|---|---|---|
| Как получаем результат | возвращаемое значение | колбэк `(err, data)` | промис → `await` |
| Блокирует поток | да | нет | нет |
| Ошибки | `try/catch` | первый аргумент `err` | `try/catch` вокруг `await` или `.catch()` |
| Плюсы | простой, предсказуемый порядок | не блокирует, самый старый и быстрый API | не блокирует, читается как синхронный, легко комбинировать (`Promise.all`) |
| Минусы | замораживает весь процесс | «ад колбэков» при вложенности, легко забыть проверить `err` | нужен `async`, чуть больше накладных расходов |
| Когда использовать | CLI-скрипты, чтение конфига при старте | старый код, максимальная производительность | новый код, серверы, обработчики запросов |

**2. Чтение файла.**
`fs.readFileSync(path, 'utf8')`, `fs.readFile(path, 'utf8', cb)`, `await fsp.readFile(path, 'utf8')`. Без кодировки возвращается `Buffer` (байты), с кодировкой — строка. Опции: `encoding`, `flag` (по умолчанию `'r'`). Весь файл попадает в память, поэтому большие файлы читают потоком: `fs.createReadStream(path)` (кусками по 64 КБ), построчно — через `readline.createInterface({ input: stream })`.

```js
const text = await fsp.readFile(path.join(__dirname, 'data', 'text.txt'), 'utf8');
```

**3. Запись файла.**
`writeFile` создаёт файл или **перезаписывает** его (флаг `'w'`), `appendFile` дописывает в конец (флаг `'a'`), флаг `'wx'` — создать, только если файла нет (иначе `EEXIST`). Есть синхронные (`writeFileSync`) и callback-варианты. Для больших/постоянных данных — `fs.createWriteStream(path, { flags: 'a' })`. Каталог должен существовать (иначе `ENOENT`) — его создают `mkdir({recursive:true})`.

```js
await fsp.writeFile('data/report.txt', report, 'utf8');
await fsp.appendFile('data/notes.txt', `Запись — ${new Date().toLocaleString('ru-RU')}\n`);
```

**4. Получение информации о файле.**
`fs.stat(path)` возвращает объект `Stats`: `size` (байты), `birthtime` (создание), `mtime` (изменение содержимого), `atime` (последний доступ), `ctime` (изменение метаданных), `mode` (тип и права, `mode & 0o777` → `644`), методы `isFile()`, `isDirectory()`, `isSymbolicLink()` (последний — у `lstat`, которая не переходит по ссылке). Существование и права проверяют `fs.existsSync(path)` (синхронно, `true/false`) или `fsp.access(path, fs.constants.F_OK | R_OK | W_OK | X_OK)` — промис отклоняется, если доступа нет. Асинхронный `fs.exists` устарел. Важно: «проверить, потом открыть» даёт гонку (файл могут удалить между вызовами), поэтому в рабочем коде чаще сразу открывают файл и обрабатывают `ENOENT`.

**5. Удаление файла.**
`fsp.unlink(path)` (`unlinkSync`, `unlink(path, cb)`) — удаляет файл; если его нет — `ENOENT`. `fsp.rm(path, { force: true })` — то же, но без ошибки, если файла нет; с `recursive: true` удаляет и каталоги со всем содержимым.

**6. Работа с директориями.**
- создание: `fsp.mkdir('a/b/c', { recursive: true })` — вся цепочка, без ошибки, если уже есть; временный каталог — `fsp.mkdtemp(prefix)`;
- чтение: `fsp.readdir(dir)` — массив имён; `{ withFileTypes: true }` — массив `Dirent` с `isFile()`/`isDirectory()`; `{ recursive: true }` (Node 18.17+/20) — сразу все вложенные пути; `fsp.opendir(dir)` — поэлементный перебор для огромных каталогов;
- удаление: `fsp.rmdir(dir)` — только пустой (иначе `ENOTEMPTY`); `fsp.rm(dir, { recursive: true, force: true })` — со всем содержимым;
- рекурсивный обход: функция читает каталог, для файлов что-то делает, для подкаталогов вызывает себя же (см. `walk()` в `task5-dirs.js`).

**7. Модуль path и обработка ошибок.**
`path` собирает и разбирает пути независимо от ОС (`/` в Linux, `\` в Windows): `path.join(__dirname, 'data', 'a.txt')` — склеить; `path.resolve('data/a.txt')` — абсолютный путь от текущего каталога; `path.basename`, `dirname`, `extname`, `parse`/`format`, `relative`, `normalize`, `isAbsolute`, `path.sep`. Пути строят от `__dirname`, а не от текущего каталога терминала, чтобы скрипт работал из любой папки.

Ошибки fs — объекты `Error` со свойствами `code` (`ENOENT`, `EACCES`, `EPERM`, `EISDIR`, `ENOTDIR`, `EEXIST`, `ENOTEMPTY`, `EMFILE`…), `errno`, `syscall`, `path`. Обрабатываются: в sync — `try/catch`, в callback — проверкой `if (err)` первой строкой колбэка, в promise — `try/catch` вокруг `await` или `.catch()`. Решение принимают по `err.code` (нет файла — создать/сообщить, нет прав — понятное сообщение и код выхода 1). Освобождение ресурсов — в `finally`. Необработанный отказ промиса (`unhandledRejection`) завершает процесс Node.js, поэтому ошибки нельзя оставлять без обработки.
